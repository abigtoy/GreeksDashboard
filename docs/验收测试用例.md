# 验收测试用例
> GreeksDashboard **v1.5** 基线验收。原始清单来源：审查意见 `审查意见260917.md` P2-4；v1.5 依据基线 §3.7/§3.8 修订（删「盯日盈亏」口径、成交账本落盘、今开仓基准、平仓成本阶梯）。
> 场景十三原结论「重启后今仓成本归零」**已作废**（v1.5 账本落盘后不再归零），本文件已按新行为改写。

## 测试环境前置条件

- CTP 连接正常（能在 09:00/13:00/21:00 收到行情）
- 结算单目录有 `full_{date}.json`（至少 T-1 和 T-2 各一份）
- 快照目录有历史快照文件
- 服务启动：`C:/veighna_studio/python.exe run_server.py`（项目目录 `C:/qproj`）

---

## 场景一：多空持仓混合

**目的**：验证方向铁律、混合仓守恒计算、OffsetFlag 归因

**步骤**：
1. 同一合约（如 `IC2609`）同时持有多头和空头
2. 昨持有多头 2 手，今开空头 1 手（开仓）
3. 今日平多 1 手（平昨，OffsetFlag=CloseYesterday）
4. 观察 dashboard 中 `IC2609_多` 和 `IC2609_空` 分别正确显示

**验收标准**：
- [ ] 多头和空头的 `direction` 字段分别正确（`多`/`空`）
- [ ] `IC2609_多` 的 pnl_today/pnl_history 与 `IC2609_空` 独立计算，互不影响
- [ ] `total_pnl_today` = Σ 各合约 pnl_today（含 realized + unrealized）
- [ ] 日志无 `fifo_fallback`（OffsetFlag 正常时）

---

## 场景二：今开今平（当日回转）

**目的**：验证平今仓的 realized PnL 正确累加

**步骤**：
1. T 日开盘后，新开 `MO2609-C-7000` 多头 1 手（OffsetFlag=Open）
2. 同日平仓（OffsetFlag=CloseToday），成交价 > 开仓价
3. 持仓 tree 中该合约消失（volume=0）

**验收标准**：
- [ ] 该合约不出现在持仓 tree 中
- [ ] `total_pnl_today` 包含该笔 realized PnL（全为已实现）
- [ ] `_realized_pnl_cache` 中有对应记录

---

## 场景三：平今/平昨 分别计算

**目的**：验证 OffsetFlag 区分 CloseToday/CloseYesterday 的归因逻辑

**步骤**：
1. 同一合约（如 `IF2609`）昨仓 3 手
2. 今日平今 1 手（CloseToday）+ 平昨 1 手（CloseYesterday）
3. 剩余 1 手昨仓（未平）

**验收标准**：
- [ ] 平昨仓位 cost_basis = settlement_cost_dict，pnl_today 基准 = Mark_T-1
- [ ] 平今仓位 cost_basis = 今日开仓均价，pnl_today 基准 = 今日开仓价
- [ ] `_realized_pnl_cache` 分别记录两条 realized 条目

---

## 场景四：全平仓后服务重启

**目的**：验证 trade_cache 幂等 + session_state 恢复

**步骤**：
1. 某合约全部平仓（持仓 volume=0）
2. 触发快照保存（空仓快照，含 `snapshot_kind: "empty"`）
3. 服务重启
4. 重连 CTP

**验收标准**：
- [ ] 重启后该合约不出现在持仓 tree（`price_basis: "closed"` 腿两条 PnL 记 0）
- [ ] realized PnL 不丢失（通过 `快照/trade_ledger.json` 重放恢复 `_REALIZED_PNL_CACHE`，v1.5）
- [ ] `snapshot_kind: "empty"` 快照覆盖前一个非空快照
- [ ] `allocation_source` 字段存在且值为 `ctp_offset` 或 `fifo_fallback`

---

## 场景五：缺结算单

**目的**：验证成本/基准降级链路（无结算单时不崩溃，且降级来源可见）

**步骤**：
1. 删除 `结算单/full_{T-1}.json`
2. 重启服务
3. 连接 CTP，观察 `pnl_today` / `pnl_history` 与 `price_basis` / `cost_basis`

**验收标准**：
- [ ] 服务不崩溃（成本降级到账本今开加权 → `position.price`；基准降级到昨收快照 → `None`）
- [ ] 日志有 `warning: settlement_file_missing` 记录
- [ ] 无基准腿 `pnl_today` 为 `null` 而非 0 或错误值，且计入 `summary.pnl_basis_counts` 的 `none`
- [ ] 接口返回中**不存在** `pnl_daily` / `total_pnl_daily` 字段

## 场景六：缺行情（未开盘）

**目的**：验证 not_opened/stale 状态

**步骤**：
1. 某合约 T 日尚未收到任何 tick
2. 查询 `/api/dashboard` 中该合约的 market_status

**验收标准**：
- [ ] `market_status` = `"not_opened"`（未开盘）
- [ ] `price_source` = `"none"`
- [ ] Greeks 全为 null，不为 0

## 场景七：夜盘跨日

**目的**：验证 TradingDay 切换、空仓快照、持仓清空

**步骤**：
1. T 日 21:00 夜盘开盘，持仓快照保存（session=N）
2. T+1 日 09:00 早盘开盘，TradingDay 从 T 切换到 T+1
3. 观察 opened_contracts/trade_cache 清空

**验收标准**：
- [ ] 快照文件名从 `data_snapshot_T_N.json` 变为 `data_snapshot_T+1_A.json`
- [ ] `opened_contracts` 和 `_realized_pnl_cache` 在切换时清空
- [ ] 空仓快照（含 `snapshot_kind: "empty"`）正确覆盖前一个非空快照

- [ ] 日志有 `warning: settlement_summary_detail_mismatch` 记录差异值
- [ ] 无 `KeyError` 或字段缺失错误

## 场景十三：成交账本落盘与重启重放（v1.5 改写，原「归零」结论作废）

**目的**：验证 `trade_ledger.json` 落盘后重启，当日已实现盈亏与今开加权成本**不归零**

**步骤**：
1. 日内对某合约开仓 + 平仓各一笔
2. 确认 `快照/trade_ledger.json` 生成，含两条 record（平仓那条带 `cost_price`/`cost_basis`/`realized_pnl`）
3. 记录当前 `summary.total_pnl_today`
4. 重启服务并等 CTP 重连

**验收标准**：
- [ ] 启动日志有 `[trade_ledger] 重放 N 笔` 且 N == 落盘条数
- [ ] 重启后 `total_pnl_today` 中的 realized 分量与重启前一致（不因重启归零）
- [ ] `record.realized_pnl` 按**落盘原值**恢复，未被重算改数
- [ ] 同一笔成交不被双计（`dedup_key` 幂等）

## 场景十四：今开仓腿基准 = 开仓价（F4）

**目的**：验证无昨结/昨收的今日新开仓腿，`pnl_today` 以账本加权开仓价为基准

**步骤**：
1. 挑一个 T-1 无持仓的合约，今日买入开仓 2 手 @ P1
2. 再加仓 1 手 @ P2
3. 读 `/api/dashboard` 该 L3 腿

**验收标准**：
- [ ] `price_basis == "today_open_cost"`，`cost_basis` 为 `settlement_cost` 缺失时的 `ledger_open_cost`
- [ ] 基准价 = (2×P1 + 1×P2)/3（加权，非末值）
- [ ] `pnl_today = direction_sign × (adjust_price − 基准) × vol × size`
- [ ] 该腿出现在 `summary.pnl_basis_counts.today_open_cost` 计数内

---

## 场景十五：CTP TradingDay 切日清零（夜盘归属）

**目的**：验证账务分区以 CTP TradingDay 为准，而非本机 clock

**步骤**：
1. 白盘（业务日 T）留有成交账本
2. 21:00 夜盘开盘后产生一笔成交
3. 观察账本 `trading_day` 字段与 `_rollover_trading_day` 日志

**验收标准**：
- [ ] 夜盘这笔 record 的 `trading_day == T+1`（下一业务日），不是自然日 T
- [ ] 切日发生时一次性清空：`_TRADE_CACHE` / `_SEEN_TRADE_IDS` / `_REALIZED_PNL_CACHE` / `_TODAY_OPEN_ACC`
- [ ] 切日日志出现且**不重复刷**（同一 TradingDay 只清一次）
- [ ] `trade_ledger.json` 的 `trading_day` 与新业务日一致；旧日账本不被当日的 reader 使用

---

## 场景十六：平昨已实现符号与成本阶梯（F3 + F2）

**目的**：验证方向枚举解析正确（不再恒判 short）、平昨成本按阶梯取值

**步骤**：
1. 持多头昨仓 N 手，今日卖出平仓 N 手（价 P，昨结算 S）
2. 另择一合约持空头昨仓，今日买入平仓
3. 再构造一笔「无昨结算、仅有今日开仓」的平昨（中金所只报「平」的降级路径）

**验收标准**：
- [ ] 多头平仓 realized 符号 = +(P − S)×N×size；空头平仓 = −(P_卖 − 成本)×N×size（**同向不反号**）
- [ ] 平昨成本阶梯：昨结算 → 今开加权 → 结算单开仓均价，命中来源写入 `cost_basis`（`prev_settlement` / `today_open_cost` / `settlement_open_cost`）
- [ ] 平今成本阶梯首档为今开加权
- [ ] 三档全无时 `cost_basis == "unknown_use_trade_price"` 且日志 WARNING，realized 记 0（不猜数）
- [ ] `record.direction` 保留原始枚举串，`trade_side`/`position_direction` 为 `long`/`short`
